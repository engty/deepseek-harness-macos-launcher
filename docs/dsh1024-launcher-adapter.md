# 1024 Store 启动器适配

## 目标与边界

固定使用 dsh1024 0.5.0，保留官方商店目录和浏览功能；商店自身不再检查或安装更新。适配代码随启动器发布，由维护者验证后手动升级。原作者来源与许可证保留在 `Resources/dsh1024-launcher/NOTICE.md`。

这里是独立的 DSH profile 和子进程环境，不是虚拟机：保留真实 HOME 与用户授权访问的工作区，通过 DSH_HOME、工具路径、包管理器前缀和缓存路径隔离安装内容。

## 已确认的问题

- 商店 HTTP 安装入口直接调用官方 CLI，绕过启动器的候选目录、依赖确认、兼容修复、启动预检和重新加载。
- 打包后的 pnpm `.modules.yaml` 含构建电脑的绝对 store 路径；原版商店会再次把该路径传给安装子进程。
- 启动环境未暴露当前 profile 的可执行目录，安装后的 CLI 工具无法通过名称找到；内置 Node 只有 node，没有 npm/npx。

## 实现步骤

1. 将需要改动的 dsh1024 文件固定到启动器资源目录，启动及候选安装时校验版本、同步适配；遇到未知版本明确报错，不套用旧适配。
2. 商店在本地完成命令解析后只返回安装意图；远程 iframe 只能通过精确匹配的 HTTPS 来源、嵌入在本地 Runtime 页面时调用受限的 WebKit 通道。原生侧再校验动作、web profile、参数和已安装包。
3. 原生流程展示确认与进度，停止当前 Runtime 后复制候选目录，执行安装、兼容修复和实际启动检查；成功后切换并启动，失败保留原配置。
4. 统一安装与运行子进程的 DSH_HOME、profile bin、Node/pnpm/npm 路径。包管理器缓存和全局式 CLI 前缀位于 App 私有目录。旧 pnpm store 的迁移只在候选目录执行。
5. 关闭商店自身的检查更新和自升级；保留目录刷新。CLI 直接修改仍需遵循启动器维护边界。

## 验收

- 从实际 dsh1024 本地路由得到合法安装/卸载意图；自更新拒绝执行且不访问更新服务。
- 原生通道拒绝远程来源、子 frame、非 web profile、不支持的命令和参数。
- 在无凭据的隔离 profile 中用真实 Runtime 安装测试插件，检查安装结果和依赖路径，再启动全部待测内置插件并创建会话。
- 失败安装不改变活动 profile；重复运行不反复改写适配或重建 pnpm 依赖。
- 本地构建与相关回归测试通过；标题栏、窗口按钮和余额样式不变。
